1. **P1, §9 line 242.** `Dispose` promises to drain accepted work and terminate the thread within two seconds. An Explorer call can itself take longer than two seconds, and a callback that calls `Dispose` must return before its own thread can exit. Define when the worker stops accepting work, what an external caller observes if the wait expires, and when the thread exits after self-disposal. Test with one callback held open and a second already queued. Every accepted caller must receive its result or exception exactly once, and a late caller must get `ObjectDisposedException`.

2. **P1, §9 lines 242 and 248.** The blocking queue has no requirement to pump Windows messages while the STA is idle. Both the apartment-state assertion and a successful `ItemCount` can pass with a worker that leaves incoming messages undispatched. Require a message-pumping wait and a bounded test that posts a message to the idle worker and observes it being handled without submitting another `Run`. [Microsoft’s STA message-loop requirements](https://learn.microsoft.com/en-us/windows/win32/com/single-threaded-apartments)

3. **P1, §9 line 243.** `RunWithView` has no acceptance check for releasing the acquired `DesktopView`. The live count succeeds even if the helper leaks the view on every call or releases it on the caller’s thread after a callback throws. Require acquisition, callback execution and disposal inside the same worker invocation. Use the existing release seam to verify exactly one release on that STA on both success and failure, with the callback exception preserved.

4. **P2, §9 lines 240 and 243–245.** The live test calls only `RunWithView`, and the four public members are tested only after disposal. All checks can pass if those members check a disposed flag and otherwise throw their section-specific placeholder directly on the caller. Add a pre-disposal test that observes worker execution through each public member and fails when any one bypasses the shared worker. The functional bodies can stay with §§3–5.

5. **P2, §9 line 244.** Getting `ObjectDisposedException` from the wrapper does not prove that disposing `ShellDesktopIcons` stops its worker. Capture the actual worker thread during a callback, dispose the wrapper twice from outside that thread, and assert that the captured thread exits. This catches a wrapper that marks itself disposed but leaves the worker running.

WPF can return an aborted operation when it cannot post the processing message. To reproduce, hold the worker in a callback, fill its Win32 message queue to capacity, then submit a second `Run` from another thread. If the dispatcher post fails, releasing the first callback never unblocks the second caller. Waiting on the dispatcher operation’s task would propagate the cancellation.
