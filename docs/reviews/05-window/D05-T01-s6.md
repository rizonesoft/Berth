**P2 findings**

1. **A partial restore or undo will offer the wrong action.** Both result factories return `Failed(NotPlaced)` when any present icon fails placement. The proposed `Undone && NotPlaced > 0` branch is unreachable, and the generic failure branch would offer Retry. Retrying Restore can overwrite the snapshot needed to undo the original restore. Handle placement outcomes before generic failures. Offer Undo after a partial restore or incomplete undo while `CanUndo` is true. A missing-only undo consumes the snapshot and has no action. Test all three through the real result factories, including a second Undo that succeeds after the first leaves an icon out of place. 2. **Successful Rename and Delete have no status sentence.** `Messages.Window` does not exist. The shared formatter is `Messages.Status(result, now, zone)`, and it explicitly throws for `Renamed` and `Deleted`. SPEC §8 defines no success row for either. On those successes, leave Working and display the refreshed selection’s comparison. Test rename with the same key and delete with a replacement selection. Use `Messages.Comparison(moved, missing)` and `Messages.OtherArrangement(savedAt, now, zone)` for the comparison rows. [Messages.cs](/D:/GitHub/Berth/src/Berth/Core/Messages.cs:35) [SPEC §8](/D:/GitHub/Berth/design/SPEC.md:94)

3. **Retry needs the original request and its arguments.** A `WindowOperationKind` cannot recover the expected arrangement key for Restore, the target key for Revert or Delete, or the proposed name for Rename. Save also has a success callback that selects the arrangement actually written. Tray failures carry even less information: `OperationFinished` publishes the result alone, so a busy refusal from Save is indistinguishable from one from Restore. Carry the repeatable request from its entry point and preserve its target, arguments, guards, and post-success selection. Test a keyed retry and a failed **tray** Save retried from the window, then read back the intended layout. [DetailViewModel.cs](/D:/GitHub/Berth/src/Berth/Window/DetailViewModel.cs) [TrayMenu.cs](/D:/GitHub/Berth/src/Berth/App/TrayMenu.cs:351)

4. **The proposed tray subscription misses Working and can lose the finished sentence on the next poll.** Tray busy changes reach `Detail.SetExternalBusy`, which does not raise `Detail.OperationStarted`. The tray also raises `OperationFinished` *before* it clears busy, and its refresh reads the tray’s active layout without updating the window comparison. Drive Working from the combined busy state, refresh the window’s comparison baseline for the completed operation, and publish the result in an order that preserves busy precedence. Unsubscribe on `Closed` alongside the existing busy handler. Test a blocked tray Restore, opening the window while it runs, and the first unchanged poll after completion. The window should show Working, then the restore sentence with Undo, and keep that sentence through the poll. Read eligibility off the UI thread on refresh while Undo is offered. If the snapshot disappears, preserve the sticky sentence and remove the button.
